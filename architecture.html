Architecture decision · app1 · GKE consolidation

One deployment, two data domains, no data movement

A Composer DAG in each domain posts its rows to a single app1 in the Global cluster, which forwards each batch to that domain's D1 as one plain-text POST — while IDL's rows keep coming to rest only in IDL, and Global's only in Global.

The shape

Composer owns the data. app1 owns the delivery.

Two requirements pull against each other. app1 should exist once, in Global. IDL data should never live in Global. The split that resolves them is a split of responsibility:

Each domain's Composer DAG reads that domain's BigQuery, renders each row to its final text line, and posts the batch to app1. app1 authenticates the caller, works out which domain it belongs to, joins the lines into one body, and POSTs that body as text/plain to that domain's D1. It then hands the outcome back, and the DAG writes it to its own results table.

app1 therefore has no BigQuery access in either project — no dataset grants, no impersonation for data, nothing to revoke but one token-minting binding. It holds no queue, no cache, no database and no disk. The rows exist in it for the duration of one HTTP request, and each domain's DAG stays the system of record.

Settle this before you decommission IDL's cluster

This design guarantees residency at rest: no IDL row is stored, cached, spooled or logged in Global. It does not give you residency in transit or in processing. IDL rows now cross the boundary twice — inbound in the DAG's request body, and outbound again in the POST to D1-IDL — passing through a process on a Global node each time. That is what “app1 lives only in Global” means under a push model.

For most residency regimes that is the line that matters. If your obligation is stricter — IDL data may not be processed outside IDL, not merely not stored there — no Global-hosted app1 can satisfy it, and you want variant B below.

Section 3

How residency-at-rest is enforced

Four independent layers, owned by different teams, so that no single mistake leaves a row in the wrong place.

01

Identity — app1 can't reach either BigQuery

The DAGs hold the dataset grants, each in its own project. app1's only cross-project grant is serviceAccountTokenCreator on an IDL-owned account used to call D1-IDL, so IDL's audit log shows an IDL principal and IDL can cut app1 off with one binding. app1 could not read an IDL table even if its code tried.

owner · IDL platform team
02

Code — the residency guard

The destination is derived from the domain bound by the caller's verified identity, never from the request body, and is re-checked immediately before the POST rather than only at client construction. A mismatch raises ResidencyViolation and the payload is dropped rather than delivered.

owner · app1 · app/residency.py
03

Network — egress allowlist and one-way PSC

A NetworkPolicy limits the pod to the two D1 endpoints and the Google APIs it needs to mint tokens. There is no BigQuery destination in that list at all. PSC is one service and one direction — app1 never dials back into IDL over it.

owner · network team
04

Platform — organisation policy

gcp.resourceLocations pins IDL resources to European regions whatever the code does. The backstop that does not depend on app1 being correct.

owner · org admin

The check that would otherwise fail silently

app1 is in raw-passthrough mode: it never reformats a line, it only joins them with \n and posts the result. That makes exactly one validation load-bearing. A line that already contains a line break would arrive at D1 as two records — an 18-row batch quietly becoming 19, with no error anywhere to reveal it. 

// the DAG sanitises when it renders...
REC-0018|C-18|42.00|EUR|2026-08-16T09:00:00Z

// ...and app1 verifies before joining. This one is refused:
REC-0018|C-18\nINJECTED|X|…
  → 422 REJECTED, nothing sent, all 18 rows stay claimable

Because the batch is a single POST, a partial send is impossible, so the default on_invalid_record: reject_batch keeps D1 all-or-nothing. Switch it to skip_record only if D1 tolerates gaps.

The subtle one: logs

app1's pods run in Global, so their stdout goes to the Global project's log bucket. Emitting an IDL record_id there would be an IDL→Global export through the back door. For domains flagged log_record_identifiers: false, log lines carry a salted digest (h:9f2c4e…) instead — enough to correlate two lines in one batch, useless as an identifier. The readable trail stays in IDL's own app1_results table, written by the IDL DAG.

Operations

When it goes wrong

What breaksWhat happens
D1 returns 5xx or times outapp1 replays the identical body under the same key, 4 attempts, exponential backoff with jitter, Retry-After honoured. Still failing → the DAG marks every row RETRY and the task fails visibly in Airflow.
D1 returns 4xxNot retried — a contract problem, not a transient one. Rows go to RETRY, then DEAD_LETTER after 5 attempts, with D1's own error text in app1_results.
A rendered line contains a newlineapp1 refuses the whole batch with the offending record_id named. Nothing reaches D1 and no row is consumed.
Airflow retries the taskThe claim already holds the rows, so the retry re-reads the same set, produces byte-identical content and the same Idempotency-Key. D1 dedupes.
Composer worker dies mid-runRows stay IN_PROGRESS; the next run's stale reaper returns anything claimed over 30 minutes ago to the queue.
IDL impersonation revoked/readyz fails and the pod leaves the load balancer. Deliberately all-or-nothing: a pod that can serve only half the domains is never in rotation.
IDL config points at Global D1ResidencyViolation at client construction. Start-up fails and the rollout is blocked before any pod takes traffic.
A batch grows past the ceilingRefused at max_records or max_body_bytes, so a runaway upstream load cannot turn one DAG run into a 100 MB POST.

Migration

Cutover

  1. Deploy alongside. Global gets app1 v3 with both domains configured. IDL's app1 keeps running; the IDL DAG is still paused.
  2. Prove the path. From the IDL Composer environment, post a batch with {"dry_run": true} through the PSC endpoint. app1 validates and assembles the body, reports the byte count and the idempotency key, and sends nothing — connectivity, identity, assembly and the residency guard confirmed in one call.
  3. Verify the audit trail. IDL's Cloud Audit Log should show app1-d1-caller@ invoking D1-IDL. If a Global principal appears, stop — the impersonation hop is not wired up.
  4. Shadow one real batch. Pause IDL's own app1, run one live IDL batch through Global, and diff app1_results against what old-app1 produced for the same rows.
  5. Switch the schedule. Unpause app1_dispatch_idl, disable the old IDL trigger.
  6. Decommission. Delete the IDL Deployment, then its Service, Gateway and image. Keep the IDL BigQuery datasets and the IDL Composer environment — they are the point.

Rollback at any step up to 5 is re-enabling the old IDL trigger. The data never moved, so there is nothing to migrate back.

Figure 3

If in-transit residency is also required

Everything above is variant A — what was asked for, and what is built. Under a push model, variant B gets simpler than it was: IDL's DAG posts to an app1 running in IDL, from the same image and the same release. Nothing crosses at all, and IDL needs no PSC hop.

Why the timing matters

Variant B needs IDL compute to still exist. Decide before cutover step 6 — once the IDL cluster is gone, moving to B becomes a re-provisioning project rather than a config change.

The code

Where each guarantee lives

composer/dag_app1_dispatch.py
One file deployed to both Composer environments. Claims rows, renders the lines, posts the batch, writes the outcomes back — all inside its own project.
app/security.py
Inbound OIDC, and which domain a verified caller may deliver to. With app1 holding no data rights, this is the control that keeps the two domains apart.
app/residency.py
The guard. Derives the destination from the bound domain and re-checks it at send time.
app/assembly.py
Joins the lines into one body and refuses any line that would split into two records at D1.
app/downstream.py
The single text/plain POST: retries, backoff, idempotency key.
app/relay.py
The request pipeline, and the per-record outcomes the DAG writes back.
config/environments.yaml
The whole domain registry. A third domain is a block here plus IAM grants — no code change.
tests/test_assembly.py · tests/test_residency.py
The suites to keep green. Each case is a concrete way a row could reach the wrong D1, or D1 could silently receive the wrong number of records.
